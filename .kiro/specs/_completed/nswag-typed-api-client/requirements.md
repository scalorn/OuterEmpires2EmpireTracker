# Requirements Document

## Introduction

Replace the hand-written `GameApiClient` (which returns raw JSON strings that every consumer must manually deserialize) with an NSwag-generated strongly-typed API client. The generated client will return strongly-typed DTO objects from every method, handle the standard API response envelope internally, and use System.Text.Json for HTTP deserialization. The generated DTOs will live in `OE2EmpireTracker.Common` targeting `netstandard2.0` so both the WinForms desktop app (.NET Framework 4.8.1) and the Faction Server (.NET 8) can share them.

This spec covers only the foundational infrastructure and a single proof-of-concept migration: the existing `GameApiFullDiscoveryTests` fixture will be migrated to the new Generated_Client to validate end-to-end correctness. Migration of production consumers (QueueSyncService, BankingService, MailService, sync schedulers, connection monitor) is deferred to a follow-up spec.

## Glossary

- **Generated_Client**: The NSwag-generated C# HTTP client class that replaces the hand-written GameApiClient, providing strongly-typed methods for every API endpoint
- **DTO**: Data Transfer Object — a plain POCO class with `[JsonPropertyName]` attributes generated by NSwag to represent API response schemas
- **Envelope**: The standard API response wrapper structure containing `success`, `returnCode`, `returnString`, `data`, and `errors` fields that wraps every API response
- **NSwag**: A .NET toolchain for generating C# API clients and DTOs from OpenAPI/Swagger specifications
- **NSwag_MSBuild**: The MSBuild integration package that triggers client regeneration at build time when the swagger spec changes
- **Swagger_Spec**: The OpenAPI 3.0 specification file at `docs/game-api-swagger.json` documenting all API endpoints
- **Discovery_Tool**: The `GameApiFullDiscoveryTests` NUnit test fixture that crawls all API endpoints via rate-limited parallel dispatch to validate data shapes and connectivity
- **Resilience_Pipeline**: The Polly retry (exponential backoff) and circuit breaker policies combined with SemaphoreSlim-based rate limiting for transient fault handling
- **Rate_Limiter**: The SemaphoreSlim-based concurrency limiter enforcing a maximum throughput of 0.9 TPS and 9 in-flight requests
- **Token_Exchange**: The OAuth2 client_credentials flow that exchanges appId + clientId + secret for a short-lived JWT

## Requirements

### Requirement 1: NSwag Code Generation from Swagger Spec

**User Story:** As a developer, I want the API client and DTOs auto-generated from the swagger spec, so that the client stays in sync with the API without manual maintenance.

#### Acceptance Criteria

1. THE NSwag_MSBuild integration SHALL generate the client from `docs/game-api-swagger.json` during the build process
2. WHEN the Swagger_Spec file changes, THE NSwag_MSBuild integration SHALL regenerate the Generated_Client and DTO classes on the next build
3. THE Generated_Client SHALL be output to `OE2EmpireTracker.Common/Client/Generated/` as a single generated `.cs` file
4. THE DTO classes SHALL be generated as separate partial classes in `OE2EmpireTracker.Common/Client/Generated/` with `[JsonPropertyName]` attributes for System.Text.Json
5. THE generated code SHALL target `netstandard2.0` and compile without errors in both .NET Framework 4.8.1 and .NET 8 consuming projects
6. THE NSwag configuration SHALL be stored as an `.nswag` configuration file in the Common project directory for reproducible generation

### Requirement 2: Strongly-Typed Method Signatures

**User Story:** As a developer, I want every API client method to return a strongly-typed object, so that I get compile-time safety and IntelliSense instead of stringly-typed JSON parsing.

#### Acceptance Criteria

1. THE Generated_Client SHALL expose one async method per API endpoint defined in the Swagger_Spec that returns `Task<T>` where T is the strongly-typed DTO for that endpoint's response schema
2. THE Generated_Client SHALL use System.Text.Json internally for HTTP response deserialization so that no public method returns a raw JSON string, JObject, or untyped object
3. WHEN a method is called, THE Generated_Client SHALL return the unwrapped data object (the `data` field from the Envelope), not the full envelope structure
4. THE Generated_Client SHALL throw a typed exception (not return a result wrapper) for error responses, exposing the Envelope `returnCode`, `returnString`, and `errors` fields so callers can distinguish success from failure without parsing strings
5. WHEN an endpoint returns no response body (HTTP 204 or empty `data` field), THE Generated_Client SHALL return `Task` (non-generic) for that method
6. THE Generated_Client SHALL accept a `CancellationToken` parameter on every async method to support caller-initiated cancellation

### Requirement 3: Envelope Handling

**User Story:** As a developer, I want the API client to handle the standard response envelope internally, so that consumers never need to unwrap `success`/`returnCode`/`returnString`/`data`/`errors` fields themselves and the envelope-unwrapping bugs that exist today are eliminated.

#### Acceptance Criteria

1. WHEN a successful API response is received (HTTP 2xx with `success=true`), THE Generated_Client SHALL extract the `data` field from the Envelope and return it as the typed DTO
2. WHEN a successful API response is received (HTTP 2xx with `success=true`) and the `data` field is null, THE Generated_Client SHALL return null (typed as `T?`) rather than throwing an exception
3. WHEN a successful HTTP response contains `success=false` in the Envelope, THE Generated_Client SHALL throw an `ApiBusinessException` containing the `returnCode`, `returnString`, and `errors` array (each entry having `field` and `error` string properties)
4. WHEN a non-success HTTP status code is received (4xx or 5xx), THE Generated_Client SHALL throw an `ApiHttpException` containing the HTTP status code and the response body as a string
5. IF the response body cannot be deserialized as a valid Envelope (malformed JSON or missing expected structure), THEN THE Generated_Client SHALL throw an `ApiDeserializationException` containing the HTTP status code and the raw response body as a string
6. THE Generated_Client SHALL parse the Envelope structure using System.Text.Json with case-insensitive property matching

### Requirement 4: DTO Generation

**User Story:** As a developer, I want separate DTO classes generated for every API response schema, so that each endpoint has a distinct type I can use in method signatures and pattern matching.

#### Acceptance Criteria

1. THE NSwag code generation SHALL produce one DTO class per distinct schema defined in the Swagger_Spec `components/schemas` section (excluding the `serviceResponse_*` envelope schemas which are handled internally)
2. THE DTO classes SHALL be plain POCOs with public getters and setters (no constructor logic, no base classes, no implemented interfaces)
3. THE DTO classes SHALL use `[JsonPropertyName("...")]` attributes from System.Text.Json for property mapping
4. THE DTO classes SHALL represent nullable schema properties as nullable reference types (e.g., `string?`) and array/collection properties as `ICollection<T>`
5. THE DTO classes SHALL live in the namespace `OE2EmpireTracker.Common.Client.Generated` separate from hand-written domain models
6. THE DTO classes SHALL be usable as response types in the Faction Server's HTTP endpoints (shared models between client and server)

### Requirement 5: Cross-Framework Compatibility

**User Story:** As a developer, I want the generated client and DTOs to work in both the WinForms app and the Faction Server, so that both projects share a single API client library without duplication.

#### Acceptance Criteria

1. THE Generated_Client and DTO classes SHALL compile under the `netstandard2.0` target framework in OE2EmpireTracker.Common
2. THE Generated_Client SHALL depend only on packages available for `netstandard2.0` (System.Text.Json 8.x, System.Net.Http)
3. WHEN consumed by the .NET Framework 4.8.1 WinForms project, THE Generated_Client SHALL function without runtime errors
4. WHEN consumed by the .NET 8 Faction Server project, THE Generated_Client SHALL function without runtime errors
5. THE existing Newtonsoft.Json dependency in OE2EmpireTracker.Common SHALL remain unchanged for file persistence operations (PlayerContext writing Alpha3.json/BaselineData.json)

### Requirement 6: Resilience

**User Story:** As a developer, I want the new client to include Polly retry, circuit breaker, and rate limiting policies, so that the discovery tool and future consumers are protected against transient failures and API rate limits.

#### Acceptance Criteria

1. THE Generated_Client SHALL apply a Polly exponential backoff retry policy (3 retries with 1s/2s/4s delays) to all HTTP requests for transient errors (HTTP 500, 502, 503, 504, and request timeouts)
2. THE Generated_Client SHALL apply a Polly circuit breaker policy (open after 3 consecutive transient failures, 30-second break duration) to all HTTP requests
3. THE Generated_Client SHALL enforce a maximum throughput of 0.9 TPS (one request dispatched approximately every 1.11 seconds) via a token-bucket or sliding-window rate limiter
4. THE Generated_Client SHALL enforce a maximum of 9 concurrent in-flight HTTP requests via a SemaphoreSlim concurrency limiter
5. WHEN an HTTP 429 response is received, THE Generated_Client SHALL pause dispatch for the duration specified in the Retry-After header (defaulting to 60 seconds if the header is absent or unparseable, capped at a maximum of 300 seconds)
6. THE Generated_Client SHALL expose an `IsCircuitOpen` property that returns true when the circuit breaker state is Open or Isolated
7. IF a request is attempted while the circuit breaker is open, THEN THE Generated_Client SHALL throw a typed exception immediately without dispatching the HTTP request

### Requirement 7: OAuth2 Token Exchange Preservation

**User Story:** As a developer, I want the existing OAuth2 client_credentials token exchange flow preserved, so that authentication continues to work without changes to the credential storage or caching logic.

#### Acceptance Criteria

1. THE Generated_Client SHALL support the OAuth2 client_credentials token exchange via POST to `/v1/auth/token` with appId, clientId, secret, and grantType fields
2. THE Generated_Client SHALL cache tokens per character (keyed by clientId+secret hash) and reuse them until expiry
3. WHEN a cached token has expired, THE Generated_Client SHALL transparently re-exchange credentials for a fresh token
4. THE Generated_Client SHALL bypass the rate limiter for token exchange requests (auth calls are not subject to data-endpoint rate limits)
5. THE Generated_Client SHALL expose a `TestConnectionAsync` method that validates connectivity via a trial token exchange

### Requirement 8: Build Integration and Regeneration

**User Story:** As a developer, I want the client to regenerate automatically during the build when the swagger spec changes, so that the generated code never drifts from the API specification.

#### Acceptance Criteria

1. THE `OE2EmpireTracker.Common.csproj` SHALL include an NSwag.MSBuild target that runs code generation before compilation
2. WHEN the `docs/game-api-swagger.json` file has a newer timestamp than the generated output file, THE build SHALL trigger regeneration
3. WHEN the swagger spec has not changed since the last generation, THE build SHALL skip regeneration (incremental build support)
4. IF NSwag code generation fails (invalid swagger spec, schema errors), THEN THE build SHALL fail with a descriptive error message
5. THE generated file SHALL include a header comment indicating it is auto-generated and should not be hand-edited

### Requirement 9: Discovery Tool Migration

**User Story:** As a developer, I want the existing discovery test tool (`GameApiFullDiscoveryTests`) migrated to use the new Generated_Client exclusively, so that the typed client is validated end-to-end against the real API before production consumers are migrated.

#### Acceptance Criteria

1. THE Discovery_Tool SHALL use the Generated_Client strongly-typed methods for all API calls, replacing every `(bool Success, string Json)` call pattern with typed DTO results
2. THE Discovery_Tool SHALL demonstrate end-to-end correctness of the token exchange flow: authenticate via the Generated_Client's token exchange method, receive a typed token response, and use the token for subsequent data calls
3. THE Discovery_Tool SHALL demonstrate the asset crawl path via strongly-typed methods: list asset locations → get location detail → get crate contents → get blueprint detail → get survey detail, with each step returning the appropriate typed DTO
4. THE Discovery_Tool SHALL operate at a maximum throughput of 0.9 TPS (one request dispatched approximately every 1.11 seconds) enforced by the Generated_Client's Rate_Limiter
5. THE Discovery_Tool SHALL operate with a maximum of 9 concurrent in-flight requests enforced by the Generated_Client's concurrency limiter
6. THE Discovery_Tool SHALL use cascading work items: WHEN an asset location list returns locations, THE tool SHALL enqueue location detail work items; WHEN a location detail returns crates, blueprints, or surveys, THE tool SHALL enqueue detail work items for each
7. WHEN the Generated_Client throws a typed exception indicating HTTP 401, THE Discovery_Tool SHALL invoke token refresh and retry the failed request once
8. THE Discovery_Tool SHALL produce a summary report at completion indicating the count of successful calls, skipped calls, and failed calls grouped by endpoint category
9. THE Discovery_Tool SHALL write raw JSON responses to the output directory organized by endpoint category (preserving the existing output structure for comparison)
