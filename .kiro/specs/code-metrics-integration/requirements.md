# Requirements Document

## Introduction

This feature integrates Visual Studio Code Metrics into the OE2EmpireTracker build pipeline. It installs the `Microsoft.CodeAnalysis.Metrics` NuGet package, adds an MSBuild `/t:Metrics` step to generate a `CodeMetrics.xml` file, and provides a `.kiro/tools/code-metrics.js` audit check that parses the XML and reports methods or types exceeding configurable quality thresholds. The check integrates into the existing `audit.js` pipeline so it runs automatically alongside the 17 existing checks.

The tracked metrics are:
- **Maintainability Index** (0-100 scale): flags methods below threshold (default 20)
- **Cyclomatic Complexity**: flags methods above threshold (default 25)
- **Class Coupling**: flags types above threshold (default 80)
- **Depth of Inheritance**: flags types above threshold (default 6)
- **Source Lines / Executable Lines**: tracked for reporting (no threshold enforcement)

A baseline mechanism allows known violations to be tracked without blocking the audit, so existing technical debt does not prevent the check from passing while new regressions are caught.

## Glossary

- **Code_Metrics_Tool**: The `.kiro/tools/code-metrics.js` Node.js script that parses CodeMetrics.xml and reports threshold violations.
- **CodeMetrics_XML**: The XML file generated by MSBuild `/t:Metrics` target, containing hierarchical metric data (Assembly > Namespace > Type > Method).
- **Metrics_Target**: The MSBuild target named "Metrics" provided by the `Microsoft.CodeAnalysis.Metrics` NuGet package that generates CodeMetrics_XML.
- **Audit_Pipeline**: The existing `node .kiro/tools/audit.js` system that runs all audit checks and reports a combined summary.
- **Threshold_Configuration**: A JSON configuration file defining the numeric limits for each metric.
- **Baseline_File**: A JSON file listing known violations that are accepted and excluded from failure reporting.
- **Maintainability_Index**: A composite metric (0-100) measuring how maintainable code is. Green (20-100), Yellow (10-19), Red (0-9).
- **Cyclomatic_Complexity**: A metric measuring the number of linearly independent paths through a method.
- **Class_Coupling**: A metric measuring the number of unique types a given type depends on.
- **Depth_of_Inheritance**: A metric measuring how deep a type sits in its inheritance hierarchy.
- **Violation**: A method or type whose metric value exceeds (or falls below, for Maintainability_Index) the configured threshold.
- **New_Violation**: A violation that is not present in the Baseline_File.

## Requirements

### Requirement 1: NuGet Package Installation

**User Story:** As a developer, I want the `Microsoft.CodeAnalysis.Metrics` NuGet package installed in the main project, so that the MSBuild Metrics target is available.

#### Acceptance Criteria

1. THE OE2EmpireTracker project SHALL have a reference to the `Microsoft.CodeAnalysis.Metrics` package in `packages.config` with `developmentDependency="true"`.
2. THE OE2EmpireTracker.csproj SHALL import the MSBuild targets file from the `Microsoft.CodeAnalysis.Metrics` package so the Metrics target is available.
3. THE package installation SHALL use the `packages.config` package management format (not PackageReference).

### Requirement 2: MSBuild Metrics Target Execution

**User Story:** As a developer, I want to run `msbuild /t:Metrics` to generate a CodeMetrics.xml file, so that code quality data is available for analysis.

#### Acceptance Criteria

1. WHEN the command `MSBuild.exe OE2EmpireTracker.sln /t:Metrics` is executed, THE Metrics_Target SHALL generate a CodeMetrics_XML file.
2. THE CodeMetrics_XML file SHALL be located at a known path relative to the project root (the default output location used by the Metrics target).
3. THE CodeMetrics_XML file path SHALL be added to `.gitignore` as a build artifact.

### Requirement 3: Code Metrics Tool Existence Check

**User Story:** As a developer, I want the Code_Metrics_Tool to handle the case where CodeMetrics.xml does not exist, so that the audit does not crash when metrics have not been generated.

#### Acceptance Criteria

1. WHEN the Code_Metrics_Tool runs and CodeMetrics_XML does not exist, THE Code_Metrics_Tool SHALL print a message indicating that CodeMetrics_XML is missing and metrics analysis is skipped.
2. WHEN the Code_Metrics_Tool runs and CodeMetrics_XML does not exist, THE Code_Metrics_Tool SHALL exit with code 0 (no findings).

### Requirement 4: XML Parsing

**User Story:** As a developer, I want the Code_Metrics_Tool to parse the CodeMetrics.xml hierarchical structure, so that per-method and per-type metrics are extracted.

#### Acceptance Criteria

1. WHEN CodeMetrics_XML exists, THE Code_Metrics_Tool SHALL parse the XML and extract metric values for each Method element.
2. WHEN CodeMetrics_XML exists, THE Code_Metrics_Tool SHALL parse the XML and extract metric values for each Type element.
3. THE Code_Metrics_Tool SHALL extract the fully qualified name (Namespace.Type.Method) for each element to identify violations.
4. THE Code_Metrics_Tool SHALL extract the following metric values: MaintainabilityIndex, CyclomaticComplexity, ClassCoupling, DepthOfInheritance, SourceLines, and ExecutableLines.

### Requirement 5: Maintainability Index Threshold

**User Story:** As a developer, I want methods with a Maintainability Index below the configured threshold flagged as violations, so that hard-to-maintain code is identified.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL compare each method MaintainabilityIndex value against the configured minimum threshold (default: 20).
2. WHEN a method MaintainabilityIndex is below the threshold, THE Code_Metrics_Tool SHALL report the method as a violation with its fully qualified name and actual value.

### Requirement 6: Cyclomatic Complexity Threshold

**User Story:** As a developer, I want methods with Cyclomatic Complexity above the configured threshold flagged as violations, so that overly complex methods are identified.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL compare each method CyclomaticComplexity value against the configured maximum threshold (default: 25).
2. WHEN a method CyclomaticComplexity exceeds the threshold, THE Code_Metrics_Tool SHALL report the method as a violation with its fully qualified name and actual value.

### Requirement 7: Class Coupling Threshold

**User Story:** As a developer, I want types with Class Coupling above the configured threshold flagged as violations, so that highly coupled types are identified.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL compare each type ClassCoupling value against the configured maximum threshold (default: 80).
2. WHEN a type ClassCoupling exceeds the threshold, THE Code_Metrics_Tool SHALL report the type as a violation with its fully qualified name and actual value.

### Requirement 8: Depth of Inheritance Threshold

**User Story:** As a developer, I want types with Depth of Inheritance above the configured threshold flagged as violations, so that deep inheritance hierarchies are identified.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL compare each type DepthOfInheritance value against the configured maximum threshold (default: 6).
2. WHEN a type DepthOfInheritance exceeds the threshold, THE Code_Metrics_Tool SHALL report the type as a violation with its fully qualified name and actual value.

### Requirement 9: Threshold Configuration

**User Story:** As a developer, I want metric thresholds to be configurable, so that I can adjust sensitivity as the codebase improves.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL read threshold values from a JSON configuration file at `.kiro/tools/code-metrics-config.json`.
2. IF the configuration file does not exist, THE Code_Metrics_Tool SHALL use default threshold values: MaintainabilityIndex minimum 20, CyclomaticComplexity maximum 25, ClassCoupling maximum 80, DepthOfInheritance maximum 6.
3. THE configuration file SHALL support the following keys: `maintainabilityIndexMin`, `cyclomaticComplexityMax`, `classCouplingMax`, `depthOfInheritanceMax`.

### Requirement 10: Baseline Known Violations

**User Story:** As a developer, I want a baseline file listing known violations, so that existing technical debt does not block the audit while new regressions are caught.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL read a baseline file at `.kiro/tools/code-metrics-baseline.json` containing an array of known violation identifiers.
2. WHEN a violation matches an entry in the Baseline_File, THE Code_Metrics_Tool SHALL exclude the violation from the new-violation count.
3. WHEN a violation matches an entry in the Baseline_File, THE Code_Metrics_Tool SHALL still report the violation in output but mark it as baselined.
4. IF the Baseline_File does not exist, THE Code_Metrics_Tool SHALL treat all violations as new violations.

### Requirement 11: Exit Code Behavior

**User Story:** As a developer, I want the Code_Metrics_Tool to exit with code 1 only when new violations are found, so that the audit pipeline correctly reports pass or fail.

#### Acceptance Criteria

1. WHEN the Code_Metrics_Tool finds zero new violations (all violations are baselined or no violations exist), THE Code_Metrics_Tool SHALL exit with code 0.
2. WHEN the Code_Metrics_Tool finds one or more new violations (not in the Baseline_File), THE Code_Metrics_Tool SHALL exit with code 1.
3. THE Code_Metrics_Tool SHALL print a summary line in the format "N findings" where N is the count of new violations, consistent with other audit tools.

### Requirement 12: Violation Report Format

**User Story:** As a developer, I want violation reports to clearly identify the offending method or type and the metric that was exceeded, so that I can quickly locate and fix issues.

#### Acceptance Criteria

1. THE Code_Metrics_Tool SHALL report each violation on a separate line containing: the metric name, the fully qualified element name, the actual value, and the threshold value.
2. THE Code_Metrics_Tool SHALL group violations by metric type in the output.
3. THE Code_Metrics_Tool SHALL print a final summary line with the total count of new violations.

### Requirement 13: Audit Pipeline Integration

**User Story:** As a developer, I want the Code_Metrics_Tool added to audit.js, so that it runs automatically as part of the standard audit pipeline.

#### Acceptance Criteria

1. THE Audit_Pipeline SHALL include an entry for the Code_Metrics_Tool with name "Code Metrics" and script "code-metrics.js".
2. WHEN `node .kiro/tools/audit.js` is executed, THE Audit_Pipeline SHALL run the Code_Metrics_Tool alongside all other checks.
3. THE Code_Metrics_Tool findings SHALL be included in the audit summary output.

### Requirement 14: Source Lines and Executable Lines Reporting

**User Story:** As a developer, I want Source Lines and Executable Lines included in violation reports for context, so that I can assess the size of flagged methods.

#### Acceptance Criteria

1. WHEN a method is reported as a violation for any metric, THE Code_Metrics_Tool SHALL include the SourceLines and ExecutableLines values in the violation detail line.
2. THE Code_Metrics_Tool SHALL NOT enforce thresholds on SourceLines or ExecutableLines (reporting only, no pass/fail).

### Requirement 15: Documentation

**User Story:** As a developer, I want the MSBuild Metrics command documented, so that team members know how to generate the CodeMetrics.xml file.

#### Acceptance Criteria

1. THE project documentation SHALL include the full MSBuild command for generating CodeMetrics_XML.
2. THE project documentation SHALL describe the purpose of the Metrics target and where the output file is located.
3. THE project documentation SHALL note that CodeMetrics_XML is a build artifact excluded from source control.
